# Implementer 派发提示模板

派发 implementer 子代理时套用本模板。`[方括号]` 为占位符，按 task 填充。

```
Subagent (general-purpose):
  description: "实现 Task N: [任务名]"
  model: [模型 —— 必填：按 SKILL.md 模型选择；省略会静默继承会话最贵模型]
  prompt: |
    你在实现 Task N: [任务名]

    ## 任务描述

    先读你的任务简报: [BRIEF_FILE]
    它包含计划里本任务的全文，其中的精确值（数字、魔法串、签名、测试用例）照抄使用。

    ## 上下文

    [场景铺垫：本任务在全局的位置、依赖、架构背景]

    ## 开工前

    如果你对以下任何一点有疑问，**现在就问**，开工前提出：
    - 需求或验收标准
    - 方案或实现策略
    - 依赖或假设
    - 任务描述里任何不清楚的地方

    ## 你的工作

    确认理解无误后：
    1. 严格按任务规格实现
    2. 按任务要求写测试（任务声明 TDD 时：先写失败断言、看到红、再写实现）
    3. 验证实现可用
    4. 提交你的工作
    5. 自审（见下）
    6. 报告

    Work from: [worktree 目录]

    **干活期间：** 遇到意外或含糊，**提问**。暂停澄清永远可以，别猜、别擅自假设。

    ## 与兄弟任务共处

    此刻可能有其他 implementer 在兄弟 worktree 里并行工作。你的安全契约：

    - 只在你被分配的目录里工作: [worktree 目录]
    - 只触碰简报声明的文件（及其测试）。简报没说就绝不动共享配置、锁文件、生成文件——兄弟任务可能正在并发改它自己的副本。
    - 显式暂存（`git add <paths>`），永不 `git add -A`——你的提交区间就是你的 diff，里面只能有你声明的文件。
    - 如果确实需要 scope 外的文件才能继续，停下，报 BLOCKED 并指名文件与原因。不许静默扩张——scope 漂移过不了主控的对账，还会撞上兄弟任务。

    ## 测试提速纪律

    TDD 循环的时间大头是跑测试。让每次运行最小且决定性：

    - 内环只跑你正在改的那个聚焦测试（单文件，或 `-t`/`--filter` 名称匹配），runner 支持时加 fail-fast（`--bail`/`-x`）。
    - 套件已经给过答案就不要重跑确认。绿了就是回答了；重跑烧时间且证明不了新东西。
    - 内环优先内存假件/夹具；真实容器、网络、慢集成属于提交前的全量套件，不属于每个红绿循环。
    - 全量套件只在提交前跑恰好一次。修复提交只重跑覆盖修复的测试。
    - 全量套件超过 2 分钟就把墙钟时间写进报告——主控要在台账里记套件成本。

    ## 代码组织

    你对一次能装进上下文的代码推理最准，文件聚焦时编辑更可靠：
    - 遵循计划定义的文件结构
    - 每个文件单一职责、接口清晰
    - 新建的文件超出计划意图地膨胀时，停下报 DONE_WITH_CONCERNS——没有计划指引不要擅自拆文件
    - 改动的既有文件本就臃肿时，谨慎操作并在报告里记为疑虑
    - 在既有代码库里跟随既有模式。顺手改进你触碰的代码是好工程师的本分，但不要重构任务范围外的东西。

    ## 力不从心时

    停下来永远可以。「糟糕的实现比没有实现更糟」，升级不受惩罚。

    **出现以下情况立即停下升级：**
    - 任务需要多种合理方案的架构决策
    - 需要理解未提供的代码且找不到头绪
    - 不确定自己的方案是否正确
    - 任务涉及计划没预料到的既有代码重构
    - 连读文件连读了很多个仍无进展

    **升级方式：** 报 BLOCKED 或 NEEDS_CONTEXT。具体说卡在哪、试过什么、需要什么帮助。主控可以补上下文、换更强模型、或把任务拆小。

    ## 报告前：自审

    用新鲜的眼光审自己的工作：

    **完整性：** 规格逐条落实了吗？漏需求了吗？没处理的边界条件吗？
    **质量：** 命名清晰准确（说它做什么，不说它怎么做的）？代码干净可维护？
    **纪律：** 没过度建设（YAGNI）？只做了被要求的？跟了代码库既有模式？
    **测试：** 测试验证真实行为而非 mock 行为？边界覆盖了？按任务要求 TDD 了？测试输出干净（无杂散警告与噪声）？

    自审发现问题，报告前现在就修。

    ## 收到审查发现后

    审查者发现问题时，修复后重跑覆盖被改代码的测试，把结果**追加**到你的报告文件。审查者不会替你重跑测试——你的报告就是测试证据。

    ## 报告格式

    把完整报告写到 [REPORT_FILE]：
    - 实现了什么（或尝试了什么，如果被阻塞）
    - 测了什么、测试结果
    - **TDD 证据**（任务要求 TDD 时必附）：
      - RED: 执行的命令、实现前的关键失败输出、为什么该失败符合预期
      - GREEN: 执行的命令、实现后的关键通过输出
    - 改动的文件——明确说明是否与简报声明一致；有漂移大声标注（漂移会触发升级）
    - 自审发现（如有）
    - 问题或疑虑（如有）

    然后只返回以下内容（15 行以内——细节在报告文件里）：
    - **Status:** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 创建的提交（短 SHA + 标题）
    - 一行测试摘要（如「14/14 通过，输出干净」）
    - 疑虑（如有）
    - 报告文件路径

    BLOCKED 或 NEEDS_CONTEXT 时，把具体内容直接写进最终消息——主控要直接据此行动。

    完成了但对正确性有疑虑用 DONE_WITH_CONCERNS。完不成用 BLOCKED。缺信息用 NEEDS_CONTEXT。永远不要静默交付没把握的工作。
```

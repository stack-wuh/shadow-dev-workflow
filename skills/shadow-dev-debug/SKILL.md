# Shadow Dev Debug — 根因调查

Bug 的修复价值在根因，不在「不报错了」。本技能把 `norms/verification.md`「调试」节与 `knowledge/bug-investigation.md`（Bug 调查保持单一上下文）操作化为可执行流程。

**定位：** 调查态技能——apply / hotfix / 日常开发中碰到 Bug 时进入，修完带着根因结论回原流程。线上急修走 `shadow-dev-hotfix`，但快车道只省流程不省根因：本技能第 1-6 步对 hotfix 同样强制。

**执行纪律：** 一切结论引用真实命令与真实输出——复现输出、实验输出、回归输出，缺一不可。未执行根因分析就改代码的修复，review 阶段直接驳回（`norms/verification.md` 调试节）。同一 Bug 的复现、调用链追踪、根因确认、最小修复和回归验证必须由主代理或一个持续保留上下文的单一代理完成；不把关联代码按文件拆给多个隔离子代理阅读，不汇总多个局部代理的「可能原因」代替完整证据链（`knowledge/bug-investigation.md`）。

**进场：** 任何操作前，先输出：`▶ [进场] shadow-dev-debug · 根因调查`

## 流程

1. **固定复现。** 先要一个稳定复现：命令、输入、环境，一条能反复打出该错误的命令。偶现 Bug 先找放大器把概率推到必现（并发、时序、边界数据、规模），放大器本身就是根因方向的证据。复现不了的 Bug 只能列假设，不能动手修。
2. **读全错误。** 错误信息、堆栈、日志、相邻的正常输出全部读完再动脑。关键意识：**首个错误状态出现的位置 ≠ 错误暴露的位置**——报错行经常在根因下游，日志里最早的异常往往才是起点。
3. **假设清单。** 按现有证据列出**至少两个**候选根因假设，每个写明「若为真，哪个最小实验能证伪它」。单一假设就是陷阱：第一个看起来合理的解释往往不是根因，而人会顺着它找支持证据。
4. **最小实验逐个证伪。** 每个假设一个最小实验：打印中间态、二分注释、最小数据集、版本对照。实验先于修改——禁止边改业务代码边「试试看」；探针式的临时打印不算修改，但要清理残留。证伪的假设连同证据记下来，防止调查绕回。
5. **锁定根因。** 根因必须同时满足：解释**全部**症状（不只报错那条）；能回答「为什么在这里、为什么是现在」；由第 4 步的真实实验输出支撑。只解释部分症状的答案不是根因，是下一个假设。
6. **最小修复。** 修在根因处，保持既有语义。判断标准：当初的补丁冲动（容差、吞异常、特判脏数据、绕过校验）在修复后**全部不再需要**。若修复让某个校验「不再触发」，先分清是「不再需要」还是「被绕过」——后者是加重不是修复。修复不改变行为契约：顺手重构、顺手优化一律不做。
7. **同源扫描。** 同一错误模式还在哪里？grep 同模式、查同函数的其他调用点、查同类资源的管理处。一次调查至少明确回答一次「还有别处吗」，答「没有」要给出搜索依据（搜了什么、范围多大）。本场景实测：对照修复漏掉同源第二处是常见疏漏，主动扫描一次的成本远低于二次返工。
8. **同上下文回归。** 复现命令重跑必须绿；既有相关探针（该仓 CI 实测 ≤ 60s 的回归套件）跑一遍防回归；结论落盘。**绿了不等于修对了**：除回归输出外，必须能用一句话向不了解此 Bug 的人讲清根因——讲不清等于没找到根因，回第 3 步。

## 红线

- 未形成书面假设就改业务代码（「先改了试试」）
- 用容差、吞异常、特判脏数据、注释校验来消除报错
- 把「测试绿了」当根因证据
- 同一 Bug 的关联代码拆给多个子代理各读一半再汇总
- 只修报错的那一处，不同源扫描
- 复现不稳定就开始修（把偶现当必现修）
- 修复讲不清根因（外行听不通的一句话都给不出）
- 调查中的临时探针、打印、注释残留进提交

## 与其他流程的关系

- apply / review 中的单步卡点：先输出 `⏸ 卡住：<现象与排查方向>`（`norms/verification.md` 进度可见性），再进本流程
- 调查结论值得沉淀为跨项目经验时，走 `shadow-dev-knowledge` 归档；根因明确后互不依赖的 lint、类型检查、测试套件可以并行，但机械验证不得重新解释根因（`knowledge/bug-investigation.md` 适用边界）

**离场：** 完成时输出：`✅ [离场] shadow-dev-debug · 根因: <一句话> · 修复: <一句话> · 回归: <复现命令> 绿`

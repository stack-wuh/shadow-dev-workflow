# 验证策略与复杂度评级

> 分级非协商：**评级可议，验证强度与评级匹配不可议**。违反匹配即阻断。
> 沿革：20260925 由「TDD 一律非协商」修订为分级制；2026-10-09 裁决取消先红仪式与默认新建测试（原文「不要写 TDD 了，太浪费时间了」）；20261010 起验收对象明确为**领域不变量**；**2026-10-11 用户裁定「完全干掉 TDD，转向 DDD」**——测试不再是门槛，既有套件降格为契约探针（见「契约探针」节）。规格来源见 `norms/domain-model.md`，本文件只规定强度与证据形态。

## 复杂度评级（propose 阶段 AI 提案，用户在 propose 确认时批准）

评级跟**风险**走，不跟预计工作量走。三要素：

1. **契约变更**：是否改变行为契约（协议 / schema / API / 权限面 / 数据格式）？
2. **触及面**：碰宿主核心或共享模块，还是纯资产 / 文案 / 孤立函数？
3. **可发现性**：改坏了立刻可见，还是要等特定运行时路径才炸？

| 级 | 判定 | 典型例子 |
|----|------|----------|
| **S** | 零行为契约变更 | 文案、注释、归档、纯声明式配置、知识卡更新 |
| **M** | 有行为但局部，不改契约 | 插件资产、独立组件、不改共享函数签名的调整 |
| **L** | 改契约 / 碰宿主核心 / 跨模块数据流 | 协议实现、命令域行为、能力白名单、哈希语义 |

评级写入 brief 正文「## 复杂度评级」节（`评级: X · 理由: … · 期望验证深度: Y`），随 propose 确认一并批准。

## 不变量与观察点（按级别）

验收对象是不变量，证据是观察点。**测试既不是门槛，也不再是默认手段**：需要长期机检的东西一律以「契约探针」形态存在，探针与观察点的分工见下节。

| 级 | 验收对象 | 达成方式 |
|----|----------|----------|
| **S** | 无行为契约变更，验结构与引用 | diff 走查 + 结构 / 引用 / 路由 / 残留扫描 |
| **M** | 本次触及的**既有**不变量保持成立 | 冒烟命令 + 每条被触及不变量一个观察点 + 走查；触及既有探针断言时同步更新（属维护） |
| **L** | brief「## 领域模型」段列出的**全部**不变量 | 每条不变量一个可追溯观察点：真实命令 + 真实输出，必须覆盖**拒绝路径**与**状态不变量**（指针不动、无半成品残留、旧路径不可回退），或 CI 全绿链接 |

## 契约探针（contract probe）三则

既有套件（`npm test`）、`scripts/check-*.mjs`、产物扫描都属**探针**：可重复执行的机器断言。探针与观察点的分工是非协商的：

1. **运行与否不是门槛，绿也不是完成证据**——探针只说明既有断言没被打破，不证明本次的不变量成立。完成证据永远是「不变量 × 观察点」的对账表。
2. **探针红必须归因**：真实回归，还是环境噪声（本机 node 139 段错误风暴、沙箱禁网、runner 挂死、子进程继承 stdin 阻塞都属后者——它们统一表现为「无输出」，与真失败同形）。归因结论写进 brief；**未归因的红灯＝未验证**，不得声称完成。
3. **进 CI 的探针必须指名它钉哪条不变量**；指不出就不进。「新增机检写成 `scripts/` 下的可重复命令，不新建测试文件」是同一条纪律的两种表述——我们只保留前者。
- 本机取不到证据时（runner 挂死、环境 139 风暴、沙箱禁网等）必须写明**证据缺口**与**替代观察点**（CI run 链接），禁止用「应该没问题」占位。本仓 `quality-gate.yml`（push main 与全部 PR）与 `publish-release.yml`（发布冒烟）已存在：**它们的 run 链接就是合法 runtime 观察点**，机器门未过一律视为未验证。
- **以探针代替观察点同样阻塞**：拿「套件全绿」冒充不变量已验证、为凑覆盖率补断言、为一次变更新建测试文件，review 一律退回。
- 评级与不变量清单同步修订：实现期风险变级或发现新不变量时，先修订 brief 再继续，不得静默跨级。

## 进度可见性（执行纪律）

> 动机：静默执行无法察觉卡死——进程空转、外部命令挂起、反复重试都表现为「无输出」，用户无从判断是慢还是死。以下条款非协商，适用于一切验证执行与 Phase 任务执行。

- **开工先报数**：开始执行前列出完整清单——探针与命令总数 N（每项一行）、任务总数 M、不变量总数 I。没有报数就开始，视为未开始。
- **逐完成一行**：每完成一个单元立即输出进度线，不允许攒批：
  - 检查项粒度：`▶ [verify] n/N <检查项> pass|fail`
  - 不变量粒度（L 级）：`▶ [inv] i/I <不变量> observed|pending`
  - 任务粒度：`▶ [task] m/M <task-id> done`
- **卡点先报**：单步执行异常时（进程空转、外部命令挂起、同一失败重复出现），先输出 `⏸ [verify|inv|task] <名称> 卡住：<现象与排查方向>`，再按调试节追根因；禁止静默重试、禁止静默长跑。
- **收口对账**：结束时输出汇总行（如 `✅ N/N 全绿 · I/I 不变量有观察点`，附命令与真实输出摘要）；收口数目必须与开工报数一致，不一致 review 阶段阻塞。

## 验证

- **触发**: 声称 "完成" "通过" "修复" 之前
- **代码流程**: 运行 Lint + 类型检查 + 与本次不变量相关的探针或真实命令，贴出命令和输出；探针红必须附归因
- **知识治理流程**: 由 `scripts/check-knowledge.mjs` 执行（卡片字段与 status 枚举、source 存在性含归档兜底、active 路由覆盖、引用死链、废弃 token 残留、孤儿规范、技能 name/description 一致性）；AI 手跑只算提交前预检，不可替代 `npm run check:knowledge`
- **观察点对账**: 逐条不变量给出观察点或其证据缺口；缺观察点的条目在 review 记为「未验证」，不得计入完成
- **深度声明**: 完成声明的验证深度按上表与 `norms/knowledge-cards.md` 的分级对齐，`runtime` 须附可追溯观察点
- **阻断**: 无验证输出的完成声明一律无效；验证强度与复杂度评级不匹配一律退回

## 调试

- **触发**: 任何 Bug、异常、测试失败、意外行为
- **流程**: 按 `knowledge/bug-investigation.md` 在单一持续上下文中追溯根因后再修
- **阻断**: 未执行根因分析就改代码的修复，review 阶段直接驳回

## 分支

- **触发**: 任何代码修改操作
- **流程**: 先建功能分支再写代码，main 只接受 merge/PR 合入
- **阻断**: 在 main 上的 commit 直接驳回

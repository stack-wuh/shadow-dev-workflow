# 验证策略与复杂度评级

> 分级非协商：**评级可议，验证强度与评级匹配不可议**。违反匹配即阻断。
> 沿革：20260925 由「一律非协商的先红仪式」修订为分级制；2026-10-09 裁决取消先红仪式与默认新建测试；20261010 起验收对象明确为**领域不变量**；2026-10-11 裁定取消默认测试门槛、既有套件降格为契约探针；**2026-10-12 用户裁定「结合起来用」并更正制度名为 SDD（规格驱动开发）**——规格层不变（不变量仍是唯一验收对象），门槛层恢复机器判定，先红后绿降格为 **L 级可选取证策略「断言优先」**。制度名、领域建模语言与门槛的分工见 `norms/domain-model.md`。

## 三层的职责（先认清在改哪一层）

| 层 | 回答的问题 | 载体 | 由谁判定 |
|----|-----------|------|---------|
| **规格层** | 验什么 | brief「## 领域模型」段的不变量清单（`INV-n` 行键） | 人写、机器查格式（`scripts/check-brief.mjs`） |
| **门槛层** | 什么不许放行 | guard 探针 + regression 探针 + brief 契约门 | **机器二值判定，不由执行者解释** |
| **取证层** | 怎么证明成立 | 观察点（真实命令 + 输出）或断言优先（先红后绿） | 执行者选择，propose 时批准，review 对账 |

> 2026-10-11 的失误在于把这三层混成一层：因为「绿不是完成证据」（取证层的认识论判断，正确），就顺手宣布「绿不是合并门槛」（门槛层的操作判断，错误），结果整个工作流只剩执行者自证。**绿不是证据，但绿可以是门槛**——这是本文件最重要的一句话。

## 复杂度评级（propose 阶段 AI 提案，用户在 propose 确认时批准）

评级跟**风险**走，不跟预计工作量走。三要素：

1. **契约变更**：是否改变行为契约（协议 / schema / API / 权限面 / 数据格式）？
2. **触及面**：碰宿主核心或共享模块，还是纯资产 / 文案 / 孤立函数？
3. **可发现性**：改坏了立刻可见，还是要等特定运行时路径才炸？

| 级 | 判定 | 典型例子 |
|----|------|----------|
| **S** | 零行为契约变更 | 文案、注释、归档、纯声明式配置、知识卡更新 |
| **M** | 有行为但局部，不改契约 | 插件资产、独立组件、不改共享函数签名的调整 |
| **L** | 改契约 / 碰宿主核心 / 跨模块数据流 | 协议实现、命令域行为、能力白名单、哈希语义 |

评级写入 brief 正文「## 复杂度评级」节（`- **评级:** X` / `- **理由:**` / `- **期望验证深度:**` / `- **取证策略:**`），随 propose 确认一并批准。**L 级必须声明取证策略**（`assert-first` | `observation`），缺失由 `scripts/check-brief.mjs` 判红。

## 不变量与观察点（按级别）

验收对象是不变量，证据是观察点。

| 级 | 验收对象 | 达成方式 |
|----|----------|----------|
| **S** | 无行为契约变更，验结构与引用 | diff 走查 + 结构 / 引用 / 路由 / 残留扫描 |
| **M** | 本次触及的**既有**不变量保持成立 | 冒烟命令 + 每条被触及不变量一个观察点 + 走查；触及既有探针断言时同步更新（属维护） |
| **L** | brief「## 领域模型」段列出的**全部**不变量 | 每条 `INV-n` 一个可追溯观察点：真实命令 + 真实输出，必须覆盖**拒绝路径**与**状态不变量**（指针不动、无半成品残留、旧路径不可回退） |

**L 级不接受「CI 绿灯链接」单独充当观察点。** CI run 只在**本机确实取不到证据**时作为**补充**观察点，且必须同时写明证据缺口是什么、为什么本机取不到（runner 挂死、环境段错误风暴、沙箱禁网）。把「CI 全绿」写成完成理由属于以门槛代替取证，review 退回。

## 门槛层：探针分层与放行判据

探针＝可重复执行的机器断言，分两类，**门槛不同**：

| 类 | 定义 | 门槛 |
|----|------|------|
| **guard 探针** | 指名守护某条 `INV-n` 的可重复机检命令（本仓 `scripts/check-*.mjs`） | **必须绿才放行**。进 CI 的前提是能从输出反查到它钉哪条不变量；指不出就不进 |
| **regression 探针** | 既有自动化套件（`npm test`、`node --test`） | **在「CI 实测耗时 ≤ 60s」的仓里必须绿才放行**；超过阈值或本机不可复现时，必须在 brief 记为证据缺口并给出补充观察点，**禁止静默免除** |

三条放行判据（缺一即不得 release，`rules/iron-laws.md` §1）：

1. **观察点闭合**：brief「## 结果」段每条 `INV-n` 都有观察点行，或显式标注证据缺口——由 `scripts/check-brief.mjs` 判定；
2. **guard 探针绿**：所有指名不变量的机检命令通过；
3. **regression 探针绿**：按上表阈值适用。

判据 1 是**完成证据**，判据 2/3 是**合并门槛**。二者不可互相替代：门槛绿不证明你做对了，证据齐不代表门没红。

## 取证层：观察点 vs 断言优先（assert-first）

默认取证形态是**观察点**（真实命令 + 真实输出）。满足以下**全部**条件时，propose 可批准 `assert-first`（先写失败断言、再写实现、断言留在既有套件）：

1. 评级为 **L**；
2. 不变量属于**可构造输入的可执行断言**——纯函数语义、命令退出码、状态文件读写、产物结构、拒绝路径；
3. 该不变量的**观察点取证成本高于写断言**（端到端复现要造临时仓 / 起宿主 / 手动比对的，属此类）；
4. 断言能**指名**它钉的 `INV-n`，且落在既有套件内（不为此新建第二个文件；确需新建时在 brief 写明原因）。

`assert-first` 是**选项不是默认**，也**不恢复**旧仪式：S / M 级新建套件断言文件一律由 `scripts/check-brief.mjs` 判红（INV-4）。判据 3 的实证依据：回归断言对「planHash 混入账簿字段」「发布链半状态」这类表格型语义最便宜，而对「指针不动、无半成品残留」这类时序状态断言最贵——后者用观察点。

## 契约探针三则（修订）

1. **门槛与证据分开**：探针绿是放行条件之一，不是完成证据。完成证据永远是「`INV-n` × 观察点」对账表。
2. **探针红必须归因**：真实回归，还是环境噪声（本机段错误风暴、沙箱禁网、runner 挂死、子进程继承 stdin 阻塞——它们统一表现为「无输出」，与真失败同形）。归因结论写进 brief；**未归因的红灯＝未验证**，不得声称完成。归因成噪声**不解除**门槛：噪声导致跑不了就记证据缺口，不能顺手当没这回事。
3. **探针必须可反查**：每个进 CI 的探针在 brief 指名 `INV-n`；同一条纪律的反面是「为凑覆盖率补断言」「为一次变更新建测试文件」——review 一律退回。
4. **夹具必须与真实数据同构**（2026-10-12 实证新增）：`scripts/check-brief.mjs` 的初版夹具按 YAML frontmatter 写、而真实 brief 是 `shadow-dev/v1` JSON，结果 9 条断言全绿而门在真实仓上静默半读。**断言绿而生产半读**是探针最坏的失效形态，凡夹具与本仓真实产物结构不一致，该断言视为无效证据。

- 评级与不变量清单同步修订：实现期风险变级或发现新不变量时，先修订 brief 再继续，不得静默跨级。
- 取证成本本身是信号：当「把套件跑全绿」消耗的时间超过取不变量观察点的时间，按本节判据 3 改用 `assert-first` 或缩范围，而不是去放宽门槛。

## 进度可见性（执行纪律）

> 动机：静默执行无法察觉卡死——进程空转、外部命令挂起、反复重试都表现为「无输出」，用户无从判断是慢还是死。以下条款非协商，适用于一切验证执行与 Phase 任务执行。

- **开工先报数**：开始执行前列出完整清单——探针与命令总数 N（每项一行）、任务总数 M、不变量总数 I。没有报数就开始，视为未开始。
- **逐完成一行**：每完成一个单元立即输出进度线，不允许攒批：
  - 检查项粒度：`▶ [verify] n/N <检查项> pass|fail`
  - 不变量粒度（L 级）：`▶ [inv] i/I INV-n observed|pending`（**行键用 INV-n**，与 `scripts/check-brief.mjs` 的输出同构，便于反查）
  - 任务粒度：`▶ [task] m/M <task-id> done`
- **卡点先报**：单步执行异常时（进程空转、外部命令挂起、同一失败重复出现），先输出 `⏸ [verify|inv|task] <名称> 卡住：<现象与排查方向>`，再按调试节追根因；禁止静默重试、禁止静默长跑。
- **收口对账**：结束时输出汇总行（如 `✅ N/N 全绿 · I/I 不变量有观察点`，附命令与真实输出摘要）；收口数目必须与开工报数一致，不一致 review 阶段阻塞。

## 验证

- **触发**: 声称 "完成" "通过" "修复" 之前
- **代码流程**: 运行 Lint + 类型检查 + 与本次不变量相关的 guard 探针与真实命令，贴出命令和输出；探针红必须附归因
- **知识治理流程**: 由 `scripts/check-knowledge.mjs` 执行（卡片字段与 status 枚举、source 存在性含归档兜底、active 路由覆盖、引用死链、废弃 token 残留、孤儿规范、技能 name/description 一致性）；AI 手跑只算提交前预检，不可替代 `npm run check:knowledge`
- **brief 契约流程**: 由 `scripts/check-brief.mjs` 执行（领域模型段存在性、`INV-n` 编号与去重、对账闭合、取证策略取值、S/M 级新建套件断言判红、archive 不追溯）
- **观察点对账**: 逐条不变量给出观察点或其证据缺口；缺观察点的条目在 review 记为「未验证」，不得计入完成
- **深度声明**: 完成声明的验证深度按上表与 `norms/knowledge-cards.md` 的分级对齐，`runtime` 须附可追溯观察点
- **阻断**: 无验证输出的完成声明一律无效；验证强度与复杂度评级不匹配一律退回；三条放行判据缺一律不得 release

## 调试

- **触发**: 任何 Bug、异常、测试失败、意外行为
- **流程**: 按 `knowledge/bug-investigation.md` 在单一持续上下文中追溯根因后再修
- **阻断**: 未执行根因分析就改代码的修复，review 阶段直接驳回

## 分支

- **触发**: 任何代码修改操作
- **流程**: 先建功能分支再写代码，main 只接受 merge/PR 合入
- **阻断**: 在 main 上的 commit 直接驳回

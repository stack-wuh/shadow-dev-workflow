# 验证策略与复杂度评级

> 分级非协商：**评级可议，验证强度与评级匹配不可议**。违反匹配即阻断。
> （20260925-feature-validation-strategy-signals 起由「TDD 一律非协商」修订为分级制，修订经用户批准；修订动机与实证见该 brief。）

## 复杂度评级（propose 阶段 AI 提案，用户在 propose 确认时批准）

评级跟**风险**走，不跟预计工作量走。三要素：

1. **契约变更**：是否改变行为契约（协议 / schema / API / 权限面 / 数据格式）？
2. **触及面**：碰宿主核心或共享模块，还是纯资产 / 文案 / 孤立函数？
3. **可发现性**：改坏了立刻可见，还是要等特定运行时路径才炸？

| 级 | 判定 | 典型例子 |
|----|------|----------|
| **S** | 零行为契约变更 | 文案、注释、归档、纯声明式配置、知识卡更新 |
| **M** | 有行为但局部，不改契约 | 插件资产、独立组件、不改共享函数签名的调整 |
| **L** | 改契约 / 碰宿主核心 / 跨模块数据流 | 协议实现、命令域行为、能力白名单、哈希语义 |

评级写入 brief 正文「## 复杂度评级」节（`评级: X · 理由: … · 期望验证深度: Y`），随 propose 确认一并批准。

## TDD 与测试要求（按级别）

| 级 | 测试要求 |
|----|----------|
| **S** | 不创建测试；验证 = diff 走查 + 结构/引用扫描 |
| **M** | 默认**不新建测试文件**；冒烟命令 + 既有测试保持绿 + 走查（见「验证方式裁决」） |
| **L** | 原「完整 TDD（先红后绿）」，2026-10-09 用户裁决后改为**可追溯 runtime 观察点**：拒绝路径与状态不变量必须真实跑过，或 CI 全绿链接 |

- 评级是 AI 提案、人批准；review 阶段检查「验证强度与评级匹配」：S 级过度测试同样指出（浪费），L 级验证不足直接阻塞。
- 实现期发现风险升/降级（如纯文档 change 需要改运行时代码）时，先修订 brief 评级再继续，不得静默跨级。

## 验证方式裁决（2026-10-09 用户裁决）

> 裁决原文：「不要写 TDD 了，太浪费时间了。」据此，**先红仪式与「为新 change 新建测试文件」不再是默认要求**；不变的是另一条——**验证强度与复杂度评级匹配仍不可议**，只是达成强度的手段换成成本更低的形态。

| 级 | 达成方式（现行） |
|----|------------------|
| S | diff 走查 + 结构/引用/残留扫描（同旧） |
| M | 冒烟命令 + 既有测试保持绿 + 走查；触及既有契约时**更新既有断言**（属维护，不算新增测试） |
| L | 可追溯 runtime 观察点：真实命令 + 真实输出，必须覆盖**拒绝路径**与**状态不变量**（指针不动、无半成品目录、旧路径不可回退），或 CI 全绿链接 |

- **既有测试必须保持绿色**——「不写 TDD」不等于「不跑测试」。
- 本机取不到证据时（runner 挂死、环境 139 风暴等），必须写明证据缺口与替代观察点（CI run 链接），禁止用「应该没问题」占位。
- 「无验证输出的完成声明一律无效」「验证强度与评级不匹配一律退回」两条阻断条款不变。
- 进度可见性条款（开工报数、逐完成一行、卡点先报、收口对账）**不变**——它治的是静默长跑，与写不写测试无关。

## 进度可见性（执行纪律）

> 动机：静默执行无法察觉卡死——进程空转、外部命令挂起、反复重试都表现为「无输出」，用户无从判断是慢还是死。以下条款非协商，适用于一切 TDD / 绿灯测试与 Phase 任务执行。

- **开工先报数**：开始测试与任务执行前，先列出完整清单——测试总数 N（每项一行）与任务总数 M。没有报数就开始，视为未开始。
- **逐完成一行**：每完成一个单元立即输出进度线，不允许攒批：
  - 测试粒度：`▶ [TDD] n/N <测试名> red|green`
  - 任务粒度：`▶ [task] m/M <task-id> done`
- **卡点先报**：单步执行异常时（进程空转、外部命令挂起、同一失败重复出现），先输出 `⏸ [TDD|task] <名称> 卡住：<现象与排查方向>`，再按调试节追根因；禁止静默重试、禁止静默长跑。
- **收口对账**：结束时输出汇总行（如 `✅ N/N 全绿`，附命令与真实输出摘要）；收口数目必须与开工报数一致，不一致 review 阶段阻塞。

## 验证

- **触发**: 声称 "完成" "通过" "修复" 之前
- **代码流程**: 运行 Lint + 类型检查 + 相关测试，贴出命令和输出
- **知识治理流程**: 检查卡片字段与分区、source 存在性、active 路由覆盖、死链接和过期执行依赖
- **深度声明**: 完成声明的验证深度按上表与 `norms/knowledge-cards.md` 的分级对齐，`runtime` 须附可追溯观察点
- **阻断**: 无验证输出的完成声明一律无效；验证强度与复杂度评级不匹配一律退回

## 调试

- **触发**: 任何 Bug、异常、测试失败、意外行为
- **流程**: 按 `knowledge/bug-investigation.md` 在单一持续上下文中追溯根因后再修
- **阻断**: 未执行根因分析就改代码的修复，review 阶段直接驳回

## 分支

- **触发**: 任何代码修改操作
- **流程**: 先建功能分支再写代码，main 只接受 merge/PR 合入
- **阻断**: 在 main 上的 commit 直接驳回
